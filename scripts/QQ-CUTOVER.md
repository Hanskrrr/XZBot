# QQ 接入切换与回退

新旧系统使用同一个 QQ Bot 时，只能保留一个接入程序。下面的脚本不会修改 DSH 的文件、关闭 DSH 或要求重新输入 API Key。

## 开始前

1. 保持 Azusa 核心服务运行：在项目目录运行 `scripts/run.sh`，管理页为 `http://127.0.0.1:6196`。
2. 在旧 DeepSeek Harness 中停止 QQ 插件，或从菜单选择“退出”完全关闭应用；只关窗口不等于退出。当前已知配置没有明确禁用字段，因此完全退出是最容易验证的方式。以后需避免 DSH 自动重启并重新连接 QQ。
3. 停止独立测试用的 AstrBot 6195 实例。在其启动终端按 Ctrl+C；不要停止 6196 的核心服务。可用 Mac 活动监视器核对该独立 Python 进程，不要结束不确定的进程。

主人和白名单已经在本项目本机配置中保存，不需要重复填写。脚本会核对 AppID、每个主人对应的群/私聊白名单、云端配置、现有安全凭据、固定依赖版本、桥接部署位置、6196 管理鉴权以及 6195 是否空闲。检测权限不足或结果不明确时拒绝启动。

## 检查与连接

在项目目录执行：

```sh
.venv/bin/python scripts/connect_qq.py --old-dsh-stopped --check
.venv/bin/python scripts/connect_qq.py --old-dsh-stopped
```

第一条只检查。第二条检查通过后同步打开本项目核心和桥接开关，读取已有凭据到内存，通过进程环境传给官方 QQ 适配器，然后以前台方式启动。没有密钥命令行参数，也不把 QQ Secret 写入 AstrBot 配置。

`--old-dsh-stopped` 是你的明确确认；脚本仍会验证旧 QQ 配置明确禁用，或系统进程列表中旧 DeepSeek Harness 主进程确实不存在。这个检查不能证明所有其他机器、CLI 或后台守护进程都已离线；如果还有其他 QQ 接入，也需先停止。运行期间不要重新启用旧接入。

首次实际验收建议：先在已允许的私聊发送短文本，确认只回复一次；请求语音，确认只收到可播放的语音；再检查主人命令与记忆查询。后台的 uncertain 表示没拿到确定回执，不应直接重发以免重复。

## 停止新 Bot，恢复旧 DSH

1. 在新 AstrBot 的前台终端按 Ctrl+C，等待退出和 6195 端口释放。
2. 在项目目录执行 `.venv/bin/python scripts/connect_qq.py --disable`。脚本要求 6195 已停止，然后关闭两个新系统 QQ 开关。
3. 重新打开原 DeepSeek Harness；如果之前手动禁用过 QQ 插件，在原界面恢复它。此项目从未更改原 DSH 配置。

6196 核心服务可以继续保留，用于管理和离线测试。切换失败时，启动前的配置写入失败或进程执行失败会恢复原开关；若 AstrBot 启动后的网络连接失败，停止该进程并执行 `--disable` 再回退。

普通 `scripts/run_astrbot.sh` 默认不连接 QQ；本机锁和端口检查会阻止本项目重复启动。升级 AstrBot 或桥接后必须重新验证；版本不匹配时切换脚本拒绝连接。
